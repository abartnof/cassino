# Review of the 3D table, 2026-10-03

A code review of the table (`web3d/src/*.js`, `web3d/test/*`) by a separate
agent, against `docs/TABLE3D.md`, `docs/PROTOCOL.md` and `docs/DESIGN.md`
§12. The table's code is as of commit 6559cd4 (T9), unchanged at the
review's HEAD (8f9e19b); untracked work in progress (`web3d/src/series.js`)
was not reviewed. No source file was changed.

**Method.** Every module and test was read. Each finding below was checked
against the code and, where practical, reproduced: in Node against the real
engine (`target/.../cassino_wasm.wasm`), or in headless Chromium on the built
page (`web3d/cassino3d.html`, the same sources), mostly on the table's
hand-driven clock (`?manual`). The reproductions are described with each
finding so they can be rerun. The Node suite passes (148 tests); the browser
test's result is at the end.

## Findings

### T1. Upright windows wider than 700 px get a negative framing band (critical)

`web3d/src/main.js:375-388` (`fitStrips`), `web3d/src/framing.js:49`,
`web3d/src/style.css:924`.

The 3D layout switches to the upright arrangement on the window's shape
(`aspect < PORTRAIT_BELOW`, 0.85), but the overlay's upright arrangement is a
media query on width (`(orientation: portrait) and (max-width: 700px)`). In
between, an upright window wider than 700 px, the overlay keeps the desktop
arrangement (the bar of icons at the top) while the table is framed as a
phone's. `fitStrips` then computes the foot strip from
`Math.min(controls.top, bar.top)`, which is the bar's top, 12 px:

| Viewport | strip top | strip foot | band left for the table |
|---|---|---|---|
| 768×1024 (iPad) | 187 | 1018 | −181 px |
| 820×1180 (iPad Air) | 187 | 1174 | −181 px |
| 1024×1366 (iPad Pro) | 187 | 1360 | −181 px |
| 900×1100 (a tall desktop window) | 187 | 1094 | −181 px |
| 390×844 (phone, for comparison) | 183 | 194 | 467 px |

**Failure.** On every iPad held upright the camera frames the hand only: the
table's middle is off the top of the screen or under the HUD and the bar
(at 1024×1366 the table cards' screen points are off screen; at 768×1024 one
is under the HUD), the opponent's hand is out of view, and the aids panel
covers the prompt. Taps meant for table cards hit the HUD or nothing (a
scripted game at 768×1024 could not make `take 10♥ A♠ 9♣`: the tap on A♠
did not pick it, and no chip came).
Reproduced by measuring the strips and hit-testing each card's screen point
at each viewport.

**Fix.** One predicate for both: drive the overlay's arrangement from
`stage.portrait` (a class on `<html>` set in `onReframe` and at start, the CSS
keyed on it) instead of the width query; at least, take the foot strip only
from elements that sit at the foot. Add a 768×1024 viewport to
`check_phone` in `browser.py`.

### T2. Watch mode stuck after a new game started during the watch pause (major)

`web3d/src/main.js:297-307` (`watchOn`), `main.js:228-231` (`newGame` calls
`director.cancelTimed()`), `web3d/src/director.js:240-242, 284-287`.

`watchOn` sets `watchStep = true` and schedules the step on the table's clock;
only that callback resets the flag. `newGame` (and `restart`) empty the
queue, so a step pending at that moment never runs and `watchStep` stays
`true` for the life of the page. Every later `watchOn` returns at once.

**Failure.** Watching a game, the person opens the settings and presses
"Watch a game" (or "New game" in the bar, then later "Watch a game") while
the cards are at rest between moves (the 650 ms pause after each). The new
watched game deals and never moves. In real
time: 3 events, still 3 after 12 s; on the manual clock: 3 events after 32 s
of table time. Only a reload recovers.

**Fix.** Reset `watchStep = false` in `newGame` (and wherever the queue is
cancelled), or keep the pending step's handle and test it rather than a
flag.

### T3. The game log button is inverted (major)

`web3d/src/chrome.js:97-98`.

`log.addEventListener("click", () => on.log(log.selected))` runs before
`md-icon-button` toggles `selected`, so it passes the old value.

**Failure.** Measured: first click, button selected, log hidden; second
click, button not selected, log open with its entries; third, selected and
hidden. The explanations aid writes only to the log, so a person who turns
it on and presses the log button sees nothing.

**Fix.** Listen for the button's `change` (or `input`) event, which fires
after the toggle, or pass `!log.selected`. A browser check that opens the
log would have caught it.

### T4. Tapping to land the cards takes the talk down, and the talk then lags (major)

`web3d/src/director.js:288-294` (`skip` runs `due(Infinity)`),
`web3d/src/overlay.js:188` (the linger timer is on the same queue),
`web3d/src/dialogue.js:58-63` (`next` survives), `web3d/src/main.js:325-331`.

`skip()` runs every queued callback, including callbacks queued while it
runs. Each line's box is shown, and its 3.2 s linger timer, queued by
`overlay.say` on the table's clock, runs in the same loop, so every box is
taken down at once. Separately, `dialogue.next` (when the last line will
have been said) keeps the skipped lines' planned end; nothing resets it but
`stop()` (undo, new game).

**Failure.** A tap during the house rules (or the count, or any move):
before, "Sweeps count?" showing; after one tap, every remaining line present
and already leaving; 0.6 s later, no boxes. Then, after skipping an 8-line
count and pressing Next hand, the opponent's "Building eight." due 900 ms
after its move is said 7.1 s later (dialogue module on a fake clock), after
the person may have moved again. At Brisk or Instant speed the same backlog
builds without any skip, because lines are paced by their length while the
cards are not.

**Fix.** In `skip()`, run what is due now but drop (or re-time to now) the
lingering and dialogue timers rather than running them; give the overlay's
linger its own wall-clock timer. After a skip, set the dialogue's `next` to
the clock (a `dialogue.skip()` beside `stop()`). Consider dropping a
backlogged line whose move is more than one move old.

### T5. A refused build says why only on its lowest card (major)

`web3d/src/selection.js:54-60` (`itemState`), `web3d/src/main.js:455-463`,
engine `crates/cassino-core/src/select.rs:139-156` (a build is named by
`item.first()`).

The offer's `why_not` names each other item by one card, a build by its
lowest. `itemState` compares only that card, so the build's other cards read
"idle": they are not dimmed, and a tap on one goes to the `pick` branch and
selects the whole build.

**Failure.** Real positions (seed 2): holding 2♥ against the 7-build
[A♠ 6♦], `why_not` names A♠; a tap on the top card 6♦ (the most visible one)
lifts the build in amber, the next offer has no moves, no chips appear, and
no reason is given; the prompt reads "Choose a card from your hand…" though
one is chosen. The same for 9♦ against [8♠ 8♦] and J♣ against [3♦ 4♦]. This
breaks §8's "A card that cannot join says why on tap".

**Fix.** Treat every card of the named item as refused: map `why_not` to
items (`state.table`) and test membership; dim the whole build.

### T6. The HUD across a hand boundary at quicker speeds (minor)

`web3d/src/hud.js:296-305` (`settleEnds`), `hud.js:339-350` (`endHand`,
`dealt`), `hud.js:262-267` (`play`).

A hand's end waits until its popups have played (`ends`), but the count's
lines are paced by the animation speed while a side's popups take 1.96 s
each. At Brisk (1.7) a count in which one side takes five lines ends about
5 s before that side's popups do. Meanwhile `dealt()` returns early (`if
(ends) return`), so the new hand gets no live block, and a popup that plays
before the drain is added to `model.live`, which is still the old hand. The
designer's contract (commit c484091, §6) is that the next score event after
`endHand()` starts a new live hand.

**Failure.** Simulated with the real widget (a stub DOM, the table's clock
by hand) at Brisk: you take cards, spades, both Casinos and three aces; Next
hand; your opponent sweeps with its first card. The ledger shows one hand,
"Hand 1 subtotal 10 – 1" with the opponent's sweep in hand 1, and no "Hand
2 · live". The totals stay right; a reload or undo rebuilds the ledger
correctly from the events (`ledgerOf`), so the two disagree.

**Fix.** Keep the ledger per hand: tag each HUD event with its hand number
(from the event) and add it to that hand's entry; let `dealt()` create the
new live block even while an end is pending.

### T7. Information shown before the cards have shown it (minor)

`web3d/src/main.js:417-424` (`show` draws `state.unseen` and the log),
called from `refresh()` in `advance()` (`main.js:277-288`) while the cards
are still to move; `web3d/src/director.js:122-123, 158-163` with
`main.js:118-124`.

The HUD, the trackers and the talk wait for the cards; three things do not:

- **Cards still out** updates when the state arrives. Measured: the line
  went from "43 cards" to "42 cards" the moment a move was sent, before the
  opponent's reply had left its hand. On a new deal it drops your dealt
  aces and Casinos about 1.5 s before the deal shows them.
- **The game log**, if open, lists the opponent's reply ("Your opponent
  builds eight: 2♦ on 6♣.") with no card moved yet, and a hand's end and
  totals before the count is played.
- **A stale `rested`.** `animate()` begins with `timeline.skip()`, which
  resolves the previous animation's idle promise; its `rested()` then runs
  (a microtask) after the new motions are queued. After "New game" pressed
  mid-motion (seed 7), the opponent's tracker read "Cards 3/27 Spades 1/7"
  before the new deal had been played. The same stale call runs
  `introduce()`, which can hold the table at the start of a motion.

**Fix.** Draw the unseen line and the log from the state the cards have
reached (in `rested`, as the trackers are). Give each animation a token and
ignore an idle callback whose token is stale.

### T8. A tutorial page opens twice (minor)

`web3d/src/director.js:158-168`, `web3d/src/main.js:264-270, 477-482`.

When nothing moves, `animate()` calls `rested()` twice: synchronously and
from the already-resolved idle promise. `introduce()` guards with
`director.held()`, but the gate it scheduled fires only on the next frame,
and `prefs.seen` is updated only when the page is shown, so the second call
schedules the same page again. On a restored sitting, `tutorialSince` is set
after `refresh()` has already run `introduce()` with 0, so the opponent's
builds from the whole restored history count as "just shown".

**Failure.** Turning the Tutorial switch on in the settings (introduction
not yet read): the introduction opens, is closed, and opens again
(reproduced). The same on reload with a page due.

**Fix.** Call `rested()` once per animation; in `introduce()` also refuse
while a gate is queued; set `tutorialSince` before `refresh()` on restore.

### T9. The pegboard after a hand scoring nothing (minor)

`web3d/src/pegboard.js:229-245` against `pegsOf` (`pegboard.js:123-131`).

`peg()` skips a side whose total did not change, so its back peg stays where
it was. `pegsOf`, which `reset` (reload, undo, new game) uses, puts the back
peg at the previous total, which is the front's hole. T9's stated invariant
("the gap is always the last hand's points") holds for `pegsOf`, not for the
live board.

**Failure.** Watched games, skill 1 against 4, 30 seeds: after 14 of 81
hands the live board differed from a reset; e.g. seed 2, hand 2: live pegs
at 0 and 1, reset both at 1. Reloading moves a peg.

**Fix.** Decide the rule (cribbage leaves the pegs alone on a zero score)
and make `peg()` and `pegsOf` agree; if the gap is to be the last hand,
move the back peg up to the front when a side scores nothing.

### T10. The hint button during motion (minor)

`web3d/src/chrome.js:269`, `web3d/src/main.js:212-216, 118-124`,
`web3d/src/director.js:261-266`.

The hint button is enabled whenever the prompt is `play`, including while the
opponent's reply is still moving. Pressing it sets `sel` and calls
`refresh()`; `rearrange()` only re-dresses while busy, and `rested` does not
lay out again. At rest the chips for the hint appear and the cards are lined
in amber, but the chosen card is not raised nor the picked cards lifted. A
tap on that card then runs `choose(sel, code)` on the same code, which
deselects it.

**Failure.** Seed 7, hints on, the manual clock: the hint button pressed
just after a move (cards moving, button enabled); at rest the chips show
"Take" for `take 10♥ A♠ 9♣`, but 10♥ sits 42 px lower on the screen than
when the same hint is pressed at rest and laid out.

**Fix.** In `rested`, re-run `director.rearrange()` when the view differs
from the placement's, or disable the hint button while busy.

### T11. Overlay overlaps at a 1024 px wide window (minor)

`web3d/src/style.css:109-121` (`.controls` spans the window, centred),
`style.css:793` (`.aids-panel` fixed at the bottom left), the HUD at the top
left.

At 1024×640 and 1024×768 (the iPad held sideways) the centred prompt's text
starts at x = 270 under the aids panel, whose right edge is at 378 ("…from
your hand, then the table cards to go with it." is all that shows); in a
screenshot at 1024×640 the opponent's speech box was half under the HUD,
and the HUD covered part of the opponent's pile. The chips stayed clear of
the panel in every hand tried. At 1280×800 nothing overlaps.

**Fix.** Start the controls to the right of the aids panel (or the panel
above the controls) below about 1200 px, and keep speech boxes clear of the
HUD's rectangle as they are kept on screen.

### T12. Cards through the table in the upright zones (minor)

`web3d/src/choreography.js:486` (the deal's `rise`), the zones in
`web3d/src/units.js:96-105`; the guard `web3d/test/choreography.test.js:104-123`.

Over 16,286 transitions (three rule sets, twelve seeds, played with undo and
`play_forced`, and watched), no path dipped below the table in `ZONES`; in
`ZONES_PORTRAIT`, 2,571 motions did, worst 0.49 cm at mid-flight, mostly
cards dealt from your opponent's stock to its hand (low, near and level in
the upright arrangement), and cards carried from it within the same
transition. The test that guards this runs only the across zones.

**Fix.** Give `rise` (or the deal in the upright zones) a clearance, and run
`throughTable` with `ZONES_PORTRAIT` too.

### T13. The hint is recomputed on every tap (minor)

`web3d/src/main.js:439`.

`refresh()` calls `engine.hint()` on every tap and state change with hints
on. The hint is a pure function of the position (PROTOCOL.md), so it cannot
change within a turn. Measured in Node over 192 decisions (Royal, aces 1 or
14): median 3.9 ms, p90 26.8 ms, max 71 ms; a phone is several times slower,
on every tap.

**Fix.** Cache the hint per state (key on `state.events.length` and
`state.saved`).

### T14. Aid switches while watching, and on restore (minor)

`web3d/src/chrome.js:262`, `web3d/src/main.js:168-180, 475-482`.

The switches show `state.aids` before the preferences. A watched game's aids
are all off, so a switch turned on while watching snaps back at the next
step, though the preference was saved. On reload, the restored sitting's
aids (from its record) win over the preferences without saying so; the next
new game then uses the preferences.

**Fix.** While watching, show the preferences; on restore, send the
preferences' aids to the engine (or update the preferences from the record).

### T15. No keyboard path to a move (minor)

`web3d/src/main.js:468-469` (cards are chosen only by a click on the
canvas), `web3d/src/overlay.js:60-69`.

Cards can be chosen only by pointing at the canvas; the hand and the table
exist nowhere in the DOM, so neither a keyboard nor a screen reader can play.
Every `show()` rebuilds the chips, so a focused chip is removed and focus
falls to the body.

**Fix.** A keyboard selection (arrow keys through the hand and the table
items, Enter to choose, the chips in a focus-kept row) and an off-screen
list of the hand and table for assistive technology; reuse chip elements
when the moves are unchanged.

### T16. URL parameters persisted; a seeded link overwrites the sitting (minor)

`web3d/src/main.js:53-55, 155, 292-294`, `web3d/src/prefs.js:104-117`.

`prefs = withUrl(loadPrefs(store), params)` and every `keep()` saves the
merged object, so `?game=royal`, `?skill=`, `?speed=` or `?tutorial=0`
become the saved defaults at the first change of any setting (or the first
tutorial page seen). With `?seed=`, the saved sitting is not restored but is
overwritten by `persist()` on the first move, so following a shared seeded
link loses the game in progress.

**Fix.** Keep the URL's overrides apart from what is saved; with `?seed=`,
do not persist (as with `?fresh`).

### T17. Talk from an empty hand on a phone (nit)

`web3d/src/director.js:213-215`.

With no cards in a hand (the count's chant: both hands are empty),
`handEdge` falls back to `ZONES[...].centre` whatever the view's zones; on a
phone the box is anchored at the across-the-table hand position seen through
the upright camera. **Fix:** use `view().zones`.

### T18. The opening wait and the words said (nit)

`web3d/src/main.js:315-321`, `web3d/src/dialogue.js:35-37`.

`openingTalk` plans the house rules with each phrase's first wording
(`plan`, `usual`); `talk` then says a random wording (`chosen`). The deal can
start before the exchange ends, or wait longer than needed, by the
difference in length (65 ms a character). **Fix:** choose the words once
(`dialogue.words`) and plan and say those.

### T19. Wording (nit)

- `web3d/src/overlay.js:218`: the sweeps tracker's title says "1 point each"
  in a game where sweeps are not scored.
- The engine's refusal reads "only a 8 can take it" (`crates/cassino-core/src/moves.rs:263`);
  the table shows it verbatim. The table's own sweep line already says
  "an 8".

### T20. Undo after a deal shows the next deal (minor; engine and design)

`web3d/src/main.js:199-211`; the session's undo.

When the person's move ends a deal, the next state includes the new deal
and the opponent's reply. Undo takes it back, and the replayed move deals
the same cards (seed 21: dealt 3♣ 6♥ 10♥ K♦, undone, dealt 3♣ 6♥ 10♥ K♦
again), so the person replays their last decision of the deal knowing their
next four cards and one of the opponent's. The same after undoing Next hand.
Undo is an aid, off by default, but this is information no player at a real
table has. **Fix (engine):** refuse undo across a deal, or let the page warn
and disable the button once a deal has come since the last decision.

## Test quality

- **Q1. The reload test does not test the page's saving.**
  `web3d/test/browser.py:285-287` sends a move through `cassino3d.engine`
  directly (the page never sees it) and writes `cassino.sitting` into
  localStorage itself, then reloads. It passes with `persist()` removed; it
  tests only `engine.restore`. Make the move by clicking and read back what
  the page stored.
- **Q2. Thirteen of the table's most important Node tests skip silently
  without the module.** The reducer against the engine, every real-game
  choreography (landing, faces, no leak, no dip), the layout's faces over
  real games, the HUD's ledger, the phrases, the tutorial's ladder and the
  staging test all `skip` when `target/.../cassino_wasm.wasm` is missing;
  `bin/gate` runs them without building it (and with a stale one, against
  an older engine). The gate's summary counts passes only. Build the module
  in the gate, or fail rather than skip when it is absent.
- **Q3. The browser leak check looks once.** `browser.py:360-364` compares
  the faces with the hand and table at the first state only. Repeat it at
  every rest in the clicked game and the watched one.
- **Q4. Gaps that let T1–T6 through.** No viewport between the phone and
  the desktop (T1); no new game started from a watched game (T2); the game
  log is never opened (T3); no check of what is said after a tap (T4); no
  tap on a refused build (T5); the HUD widget (`createHud`: queue,
  `endHand`, `dealt`) has no test at all, only its model (T6), and the
  browser test waits for the HUD to be idle before pressing Next, the one
  moment it is correct.
- **Q5. Fixed sleeps.** Dialogs are awaited with `wait_for_timeout`
  (`browser.py:128, 180, 186, 195, 200, 209, 253, 258, 297`) rather than
  for a condition (`tutorialOpen()`, the dialog's `open`), which is slow
  and can flake on a loaded machine.

## Checked and found sound

- No face is ever assigned to an anonymous mesh except as the person may
  know it: over 16,286 transitions every reveal was of a card in a hand,
  on the table, in an event of the transition, in the count, or a sweep
  card already shown (a flagged QD was a sweep card going back to its pile
  on an undo of Next hand).
- Every choreography landed exactly on `layout(next)`, with no two motions
  of one mesh overlapping and each mesh showing the face it rests with, in
  both zones, with undo, `play_forced`, sweeps off, aces 1 or 14, and
  watched games stepped one move at a time. Beats were in order.
- Every phrase that `speech()` asked for over 120 watched games is in the
  bank.
- The tutorial's gate cannot deadlock: undo and new game release the clock,
  and a second gate waits behind the first.
- Preferences survive storage that throws or holds nonsense; a refused
  restore falls back to a new game; a game over is not kept.
- The HUD's port matches the handoff's numbers (segments, popup sizes and
  timings, the three springs, the ledger's heights, reduced motion).

## The browser test

`web3d/test/browser.py` passes on the built page ("browser: ok"). That is
consistent with the findings: it never uses a tablet viewport, never opens
the log, never starts a game from a watched one, and waits for the HUD to
be idle before each Next hand (Q4).
